# Proposal: sponsor-chat-streaming

**Date**: 2026-10-07
**Status**: Shipped (2026-10-07)
**Closes**: #33
**Supersedes**: unit `001-sponsor-chat-streaming` (local branch, never merged; its data-loss / id-keying / init-loop fixes shipped via #25/#28/#31, leaving only streaming)

## Goal

Stream Sponsor replies into the chat as Gemini produces them, through a NEW additive tRPC procedure, while every existing procedure (`conversation.sponsorChat`, `retrySponsorChat`, …) keeps its exact input/output/behavior for released App Store builds. The stream must degrade gracefully: if DigitalOcean's edge buffers the response the reply still arrives complete (just not incrementally) and persisted; if the stream fails mid-way there is no duplicate user message, no lost completed reply, and the existing Retry path recovers.

## Why

GitHub issue #33 (epic #34, Wave 3). Today a send waits for the full Gemini response (seconds of "Thinking...") and then appends it. Waves 1–2 shipped the building blocks this needs: persist-before-generate (`persistMessage`), the per-conversation turn lock (`withConversationLock`), `generateReply` shared by `sponsorChat`/`retrySponsorChat`, the id-keyed client cache, and the failed-send classification + "No reply yet · Retry" UI. The superseded unit 001 proposed a two-step POST-then-SSE design gated on a transport spike it could not execute.

Production topology (001's finding, corrected): `www.soberjourney.app` → DigitalOcean App Platform's DO-managed edge (Cloudflare-backed internally; the owner has no Cloudflare account, so nothing is configurable by us beyond our own response headers) → Express. Incremental delivery through that edge cannot be verified before deploy.

## Approach

### Candidates considered

- **A. tRPC SSE subscription, two-step.** POST mutation persists the user message and returns its id; a GET `httpSubscriptionLink` subscription `{conversationId, messageId}` streams the reply (retry-shaped). Uses the existing unused plumbing (`CustomEventSource`, `rn-eventsource-reborn`, `eventsource`). Two-step is forced because SSE input travels in the query string and `pino-http`/edge access logs record URLs (plaintext messages would defeat at-rest encryption). Needs idempotent replay because EventSource auto-reconnects. `text/event-stream` is the content type edges are most likely to pass through unbuffered.
- **B. Streaming mutation over `httpBatchStreamLink` (chosen).** One new mutation `conversation.streamSponsorChat` (same input schema as `sponsorChat`) whose resolver is an async generator; tRPC v11 streams it as chunked JSONL over a single POST. Message text stays in the body. The whole turn runs under the same lock as `sponsorChat`. Mutations never auto-retry (`retry: false`) and there is no EventSource, so nothing can re-send a message on reconnect — the issue's "EventSource auto-reconnect can never re-send (idempotency key)" task is satisfied by design, with no key needed. Native uses `expo/fetch` (Expo SDK 54, streaming `response.body`, winter `TextDecoderStream`) plus the already-installed stream polyfills; web uses the browser `fetch`.
- **C. Hand-rolled Express `POST` SSE endpoint outside tRPC.** `text/event-stream` with a POST body, but bypasses tRPC context/auth/typing and needs a hand-written client parser and protocol.

B chosen (3/3 panel): single request, no URL-logging problem, no reconnect/replay machinery, reuses the turn pipeline 1:1. Its weaker point — that a chunked `application/json` body may be more likely than `text/event-stream` to be buffered by an edge — is **unverified either way**; it is mitigated by anti-buffering headers and a JSONL keep-alive ping, and failing that degrades to today's behavior (whole reply at the end). Switching later to A or to a `text/event-stream` variant would also be additive.

### Server (additive only)

1. **Gemini streaming datasource** — `datasource/gemini/chatStream.mts`: `chatStream(logger, client, contents, config, model?)` is an async generator over `client.models.generateContentStream` (60 s timeout; `config.abortSignal` passed through) that yields text deltas and **returns** a `ChatResult` (`ok` / `blocked` / `truncated`) classified at the end from the accumulated text + last `finishReason`/`promptFeedback`; it throws `GeminiError` (`rate_limited` / `unavailable` / `unknown`) like `chat()`. Classification and error mapping move into shared helpers in `chat.mts`; `chat()`'s exported shape and behavior are unchanged (its tests stay green). Exported from the wrapped `datasource/gemini/index.mts` as a function only (wrapped-exports constraint). An abort is rethrown as-is (not logged as a Gemini error).
2. **Shared turn pipeline** — `runSponsorChat.mts` is split into helpers without changing behavior: `startTurn(ctx, userId, tz, input, now, { signal?, onSaved? })` (ownership check ∥ `journey.list` → `signal.throwIfAborted()` → persist the user message → `onSaved(id)` → THEN read history page + check-ins; persist-before-read-history order preserved; `sponsorChat` passes no options), `buildGeneration` (history + system prompt from `generateReply`'s current code) and `finishReply` (result → reply text / error via the existing `fallbackReplyFor` mapping, persist MODEL once, fire-and-forget title). `generateReply` = buildGeneration → `gemini.chat` → finishReply, so `runSponsorChat` and `runRetrySponsorChat` keep calling it unchanged. Existing tests (which inject `ctx` mocks, not module mocks) stay unmodified and green.
3. **`conversation.streamSponsorChat`** (new mutation, input = `chatInput`). Resolver = `async function*` yielding events:
   - `{ type: "saved", userMessageId }` right after the user message is persisted (emitted from `startTurn`'s `onSaved`, before history reads and generation);
   - `{ type: "delta", text }` per non-empty Gemini chunk;
   - `{ type: "done", response, userMessageId, modelMessageId }` after the MODEL reply is persisted — `response` is the authoritative full text; the client replaces the streamed partial with it.
   Product rules carried over: persist-before-generate (user message kept on any failure); the reply is persisted only when complete, exactly once; a mid-stream safety block (`SAFETY`/`PROHIBITED_CONTENT`) persists and returns `SAFETY_FALLBACK_REPLY` (with its conditional crisis line) and other blocks `BLOCKED_FALLBACK_REPLY` — the partial text already streamed is never persisted or logged, and the client replaces it with the fallback; `MAX_TOKENS` is never stored (error after partial deltas); rate limit → `TOO_MANY_REQUESTS`, else `InternalServerError("Failed to generate response.")` (never UNAUTHORIZED); title generation as today. Errors thrown before or after `saved` reach the client as tRPC errors in the stream.
   **Lock bridge (channel):** the turn runs inside `withConversationLock` as a producer that pushes events into an in-memory channel; the generator drains the channel. The channel is unbounded (≤ one reply's text, ~2048 tokens), is closed on every exit path (done / throw / abort), and the producer's promise always has a rejection handler, so an error after the consumer has gone is never an unhandled rejection. A lock-wait timeout (20 s) behaves exactly as for `sponsorChat` (proceeds unserialized, logged).
   **Abort** is driven by the request `signal` (tRPC's Express adapter aborts it on `res` close / `req` aborted), not by `generator.return()` (which cannot interrupt a pending await): the signal aborts the Gemini call (and `throwIfAborted()` runs after every streamed chunk, so the SDK is not relied on alone) and wakes a consumer blocked on the channel; the generator's `finally` also aborts on an early return. Effects: if aborted before the user message is persisted (e.g. while queued on the lock) the turn is skipped entirely; if aborted mid-generation nothing more is persisted (no partial reply) and the lock is released; the saved user message stays unanswered and the existing Retry UI covers it. A generation that already completed still persists its reply exactly once (abort is not checked between completion and persist). With a buffering edge, the origin may notice a client abort late — the turn may then complete and persist, which the client's refetch shows (`answered`).
4. **Edge headers + keep-alive** — `network/rpc/streamResponseMeta.mts` exports one `responseMeta` used by `createExpressMiddleware` (and imported by its HTTP test): when `info?.accept === "application/jsonl"` it adds `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`; for anything else (including `info` undefined on early errors) it returns `{}` and never throws. tRPC's own `vary: trpc-accept` and content type (`application/json`) are untouched. `initTRPC.create({ jsonl: { pingMs: 5000 } })` makes tRPC write a whitespace keep-alive during idle gaps of JSONL streams only (the option is read only in the JSONL branch, so non-stream responses are unchanged). Only tRPC's `httpBatchStreamLink` sends `trpc-accept: application/jsonl`; released apps use `httpBatchLink`, so every released-app response is unchanged.

### Client

5. **Transport** — `TRPCProvider`: `splitLink` routes `op.path === "conversation.streamSponsorChat"` to `httpBatchStreamLink` (same URL, superjson, header function, `maxItems: 1`, `fetch` from `utils/streamingFetch`, which is `expo/fetch` on every platform — its web build is `globalThis.fetch`, so no platform file is needed), everything else to the unchanged `httpBatchLink`. Removed: the `httpSubscriptionLink` branch, `utils/CustomEventSource/*`, and the `eventsource` + `rn-eventsource-reborn` dependencies (no other importers; lockfile and native autolinking change accordingly). Kept: `@azure/core-asynciterator-polyfill` and `web-streams-polyfill`. Expo 54's Metro already injects `ReadableStream`/`TransformStream`/`WritableStream` on native (`expo/virtual/streams.js`), so the provider only installs all three from the app's polyfill when any is missing (never mixing implementations) — a no-op under Expo 54. `useTRPCClient` is exported for the vanilla streaming call.
6. **Send flow** (`ConversationProvider.sendMessage`): same pending bubble keyed by client id; consume the stream with a per-send `AbortController` inside `useMutation({ mutationFn })` (so errors reach the global MutationCache auth handler); each event is folded by the pure `applyStreamEvent` reducer and the state's text becomes the conversation's pending `replyText` and render as a growing MODEL bubble with id `${clientId}-reply` (the id the final reply gets in the cache, so no remount); `ThinkingIndicator` shows only until the first delta. On `done`: append `[userMessage, reply(done.response)]` to the newest page as today, clear pending. On any error (stream error, mid-stream disconnect, buffered-then-failed, client-side transport failure): the existing failure path unchanged — trim-and-refetch the newest page, `classifyFailedSend` → `not-saved` (restore draft) / `saved-unanswered` (Retry) / `answered` (reply shown; `answered` always wins). A received `saved` event forces at least `saved-unanswered` (even if the refetch fails). A failure with no `saved` and no error response from the server (Stop, dropped connection) is re-checked once after 1.5 s before the draft is restored, so a late server persist is not re-sent. The client never re-sends automatically after a failure.
7. **Cancel** — a Stop button replaces Send while a send is in flight for the current conversation (also under a buffering edge, where nothing has arrived yet — the abort still cancels the request). It aborts that send's controller; a cancelled send runs the same refetch/classify path but shows no error toast (saved message → "No reply yet · Retry"; not saved → draft restored; answered → reply shown).
8. **Conversation switching** — pending/stream state stays per conversation (the #28 model): a stream for X writes only X's pending entry and X's cache; switching away and back shows the in-progress reply; nothing leaks into another conversation.
9. **Rollout fallback** — only when the stream call fails **before any event**, not aborted, with `TRPCClientError` `data.code === "NOT_FOUND"` and `data.path === "conversation.streamSponsorChat"` (tRPC's unknown-procedure error, which a server without the procedure returns in the same JSONL error shape — checked against real tRPC output in a server test and an ad-hoc Node client run) does the send fall back to `conversation.sponsorChat` via the vanilla client with the same abort signal (old non-streaming flow). The procedure's own pre-save "Conversation not found." matches too; the fallback then fails the same way with nothing saved. An unknown procedure never runs, so nothing was persisted and the fallback cannot duplicate. Any other pre-event failure (transport, 5xx) goes through the classify path above, never an automatic re-send. Deploy order is server first, so this is belt-and-braces for a rollback, as the issue asks.
10. **Retry stays non-streaming** — `retrySponsorChat` is unchanged and still used by the Retry action (a streamed retry is a possible follow-up).

### Verification

- **Server node tests** (`node:test`, ctx-injection pattern): `chatStream` (deltas + ok; safety block after partial text → blocked; MAX_TOKENS → truncated; empty → GeminiError; SDK error mid-stream → kinds; abort passes `abortSignal` and rethrows); stream turn (event order saved → deltas → done; user persisted before generation; Gemini failure after `saved` keeps the user row, stores no MODEL row, surfaces the mapped error; blocked → fallback persisted once and returned in `done`; truncated → error, no MODEL row; abort mid-stream → no MODEL row, lock released (a following turn runs); abort while queued on the lock → nothing persisted; abort while the consumer is blocked on the channel ends the generator; missing conversation → NOT_FOUND); channel helper; an HTTP test that mounts a tiny tRPC router (same `initTRPC` options + the production `responseMeta`) on Express: JSONL request has the anti-buffering headers and receives a chunk before the generator finishes; a non-JSONL request's status, body and headers match the same router without `responseMeta`; an unknown-procedure JSONL call yields `NOT_FOUND` with the path (fixture for the client fallback rule).
- **Ad-hoc Node e2e** (real `@trpc/client` `splitLink` + `httpBatchStreamLink` against Express with the production `responseMeta` + ping): events arrived incrementally, a 6 s idle gap survived, client abort aborted the server signal, unknown procedure produced the fallback error shape.
- **Client** (no test runner, per repo convention): pure helpers (pending merge with a streaming reply bubble; missing-procedure detection; stream-event reducer) checked by a committed `.minerva/work/2026-10-07-sponsor-chat-streaming/verify-sponsor-chat-streaming.ts` run with `npx tsx` (same convention as `2026-10-06-conversation-management`); `tsc --noEmit` and `expo lint`.
- **Manual (gating before the native release, listed in the PR):** iOS + Android dev build (Hermes) and web: reply streams incrementally against a local server; Stop; switching conversations mid-stream; safety-block replacement; failure → Retry. Removing `rn-eventsource-reborn`/`eventsource` changes the native module set, so dev clients and the next native build must be rebuilt (release note). If the native transport (`expo/fetch` + JSONL consumer) fails on device, the fix before the native release is to route native sends through `sponsorChat` (one-line client switch); the server change is safe to ship regardless.
- **Post-deploy:** an exact `curl -N` command against production that timestamps each JSONL line, to confirm incremental delivery through DO's edge.

### Compatibility statement

API contract: additive only. New procedure `conversation.streamSponsorChat` (mutation, streamed). No existing procedure's input, output, or behavior changes; the `sponsorChat`/`retrySponsorChat` refactor is behavior-preserving and pinned by their unchanged tests. Response headers and the JSONL ping apply only to `trpc-accept: application/jsonl` requests, which no released build sends. No schema migration. No new npm dependency (two removed).

## Success criteria

1. `conversation.streamSponsorChat` exists as a new mutation with `sponsorChat`'s input schema and streams `saved` → `delta`* → `done`; `done.response` equals the persisted reply; server tests prove the user message is persisted before Gemini is called and kept on failure, and that errors after `saved` surface as mapped tRPC errors.
2. Mid-stream safety block persists exactly one MODEL row with the right fallback (SAFETY/PROHIBITED_CONTENT → `SAFETY_FALLBACK_REPLY`, others → `BLOCKED_FALLBACK_REPLY`) and returns it in `done`; `MAX_TOKENS` stores no MODEL row; Gemini errors map to `TOO_MANY_REQUESTS` / `INTERNAL_SERVER_ERROR`, never `UNAUTHORIZED` — each pinned by a test.
3. A signal abort mid-stream aborts the Gemini call, persists no MODEL row and releases the lock; an abort while queued persists nothing; an abort while the consumer waits on the channel ends the stream; an abort arriving after generation completed still persists the reply exactly once — pinned by tests.
4. The HTTP test shows: JSONL responses carry `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no` and deliver a chunk before the generator completes; a non-JSONL response is identical (status, body, headers) with and without the production `responseMeta`; an unknown-procedure JSONL call returns `NOT_FOUND` with its path.
5. `sponsorChat`, `retrySponsorChat`, `chat()` and every other existing procedure are unchanged: their existing tests pass unmodified.
6. Client code: `TRPCProvider` routes only `conversation.streamSponsorChat` through `httpBatchStreamLink`; `CustomEventSource`, the `httpSubscriptionLink` branch and the `eventsource`/`rn-eventsource-reborn` deps are removed; `ConversationProvider` streams into a `${clientId}-reply` bubble, exposes Stop, falls back to `sponsorChat` only on the unknown-procedure error before any event, and reuses `classifyFailedSend` for every other failure; the verify script passes (merge, fallback detection, event reducer — including all events delivered in one burst as through a buffering edge, and a stream cut after the reply was persisted resolving to `answered` via `classifyFailedSend`). Behavior beyond the pure helpers is checked by code review plus the gating manual checklist.
7. `npm run build` (incl. app `tsc --noEmit`), `npm run test`, server lint and `npx expo lint` in `packages/app` are green (any pre-existing `expo lint` failure on the base branch is reported, not introduced); the PR body states the API-contract line, the gating manual checks (iOS/Android/web streaming, Stop, switching, safety replacement, failure → Retry) and the post-deploy curl check.

## Open Questions

- Streaming the Retry action (deferred; Retry stays on `retrySponsorChat`).
- Whether DO's edge streams chunked `application/json` incrementally is only knowable post-deploy (the curl check). If it buffers, the follow-up is a `text/event-stream` variant or design A — both additive.
- A client idle timeout for a stream that stalls after its first chunk is not added (Stop is the manual escape; the server's 60 s Gemini timeout bounds the turn).
