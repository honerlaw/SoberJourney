# Proposal: security-audit-hardening

**Date**: 2026-11-03
**Status**: Draft

## Goal
Close, or explicitly document the residual risk of, every finding from the 2026-11-03 security audit of SoberJourney, in one PR, without breaking App Store builds that are already released (they keep calling the current server forever):

1. Decrypted journal/chat/check-in data likely reaches Sentry (app `loggerLink()` logs every tRPC input+result in production; Sentry RN records console breadcrumbs and syncs them to the native scope at full depth, attached to native crash/ANR/app-hang events).
2. One request can tie up the encryption threadpool: tRPC 11.8 has no batch-size limit, so `/api/trpc/journal.list,journal.list,...` (hundreds of calls) decrypts every entry once per call (1000-iteration PBKDF2 per value).
3. No write limits or quotas outside sponsor chat (journal entries up to 100k chars each, uncapped conversations/journeys; `journal.list` unpaginated); every authenticated request writes the user row.
4. CSRF exposure: tRPC accepts `multipart/form-data` POSTs (a CORS "simple" type a cross-site form can send); `user.remove` takes no input; Clerk `authorizedParties` unset (azp unchecked, cookie auth accepted cross-origin); protection rests on `__session` SameSite=Lax, which clerk-js switches to None inside cross-origin iframes; no `frame-ancestors`.
5. No security headers (CSP frame-ancestors, HSTS, nosniff, referrer-policy; `x-powered-by` on).
6. Notification taps call `router.push(data.url)` unchecked (expo-router opens absolute URLs externally); Expo push is sent without an access token.
7. DB helpers that rely on callers for ownership: `checkin.getOrCreate` upserts by `journeyId` before checking ownership; `schedule.remove` / `schedule.getByCheckInId` take no `userId`.
8. Vulnerable server deps: `@clerk/express`/`@clerk/backend` (GHSA-w24r-5266-9c3c, not exploitable here), `body-parser` (compressed-body DoS, applies), `path-to-regexp`.
9. Production deploys via DigitalOcean's Node buildpack, so nothing in the repo guarantees `NODE_ENV=production`; tRPC `isDev` (unset in `router.mts`, so tRPC's own `NODE_ENV !== "production"` default applies) and Clerk `debug` both fail open (stack traces in error responses). Plain `Error` messages pass through to clients as INTERNAL_SERVER_ERROR messages.
10. Minor: conversation lock keyed by attacker-supplied `conversationId` before ownership check; dead token-string branch in `createContext`.

Residuals this unit documents rather than closes (each in a knowledge `reference` entry and the final report):
- Finding 1: the app fix reaches only binaries that receive the over-the-air update (a FINISHED production build sharing main's fingerprint). Binaries from before expo-updates keep logging until users upgrade. Events Sentry already holds stay there; purging or scrubbing them in the Sentry project is a user action. `sendDefaultPii` is not set (Sentry's default is off) and no replay integration is configured, so breadcrumbs are the channel this unit closes.
- Finding 4: cross-site CSRF is closed by default (see Approach: a JSON-only POST forces a CORS preflight, and the server never allows credentialed cross-origin requests). Same-site token reuse from a sibling subdomain stays possible until the user sets `CLERK_AUTHORIZED_PARTIES`.
- Finding 5: a full script/style CSP is deferred; only `frame-ancestors` (plus the other headers) ships.
- Finding 6: the push-token takeover (any user can claim a token string they know) cannot be closed server-side; Expo enhanced push security needs a dashboard toggle by the user.
- Finding 8 (only if the dependency bump is dropped by the fingerprint fallback): the vulnerable versions stay; a GitHub issue records the bump and the final report tells the user this finding remains open.
- Finding 9: whether DigitalOcean sets `NODE_ENV=production` is for the user to confirm; the code becomes safe either way.

Audit verdict that stands: no cross-user data access was found; every procedure scopes by the session user.

## Why
The app holds people's sobriety journals and AI-sponsor chats. Server-side encryption at rest is undone if plaintext ships to a third party (finding 1). Any free account can degrade service for everyone (2, 3). Account+data deletion is one forged request away under some browser conditions (4). The user asked for all findings fixed in one unit, through minerva.

## Approach
Approach **A — in-process, cost-aware controls; additive and tolerant for released apps** (approach panel 3/3). One unit, one PR, no phases (scope panel 3/3).

**Delivery and rollback.** The PR is built as one commit per control, with the app commits separate from the server commits. A bad server control is backed out by its env knob below where it has one, or else by reverting only its commit. Reverting an app commit publishes an over-the-air update too, just as a whole-PR revert would. Reverting the whole PR would also publish an over-the-air update of the old app and bring the Sentry leak back, so that is not the rollback path. App rollback uses `eas update:republish --group <previous>` or `eas update:roll-back-to-embedded` (knowledge: EAS Update on merge). If one server control stalls review or CI, it is split out of the PR and the rest ships.

**Released-client evidence** (git history holds every released build's source): across every commit to `packages/app/src`, the only parallel construct is `Promise.allSettled` over the few sign-out tasks in `useAuth/endSession.ts`. There are no looped or fan-out mutations. Every `TRPCProvider` link config (d9b51f4 → a7510b7) uses `httpBatchLink`, plus `httpBatchStreamLink` with `maxItems: 1` since a7510b7. The only non-tRPC request is `GET /api/app/config`, outside `/api/trpc`; nothing sends multipart, forms or `sendBeacon`. Released clients treat errors as follows (knowledge: released-app compatibility, plus `isNonRetryableError` since cc33521): `UNAUTHORIZED`, HTTP 401 or a message containing "Token expired" / "Invalid token" log the user out; mutations never retry; queries retry up to 3 times on 408, 429 and 5xx, and not on other 4xx (400, 403, 415).

**Review focus** (security-critical): the request guard, the decrypt budget, the errorFormatter, the ownership changes, the mutation limiter, the user upsert, and the `@clerk/express` bump.

**App (JS only, ships over the air; native fingerprint must not change):**
- `TRPCProvider.tsx`: `loggerLink({ enabled: () => __DEV__ })`.
- `AppLayout.tsx` Sentry.init: `beforeBreadcrumb` that drops `category === "console"` breadcrumbs and strips query strings from http (xhr/fetch) breadcrumb URLs; `tracesSampleRate` 1.0 in `__DEV__`, 0.1 otherwise. The scrub logic lives in a pure, import-free module checked with `node --experimental-strip-types` (the app has no test runner; same pattern as `getErrorMessage.ts`).
- `usePushNotifications.native.ts`: navigate only when `data.url` is a relative in-app path starting with `/(auth)/` (reject `//`, `\`, any `scheme:`); otherwise land on the dashboard. Pure helper, same checking method.

**Server (deploys on merge; additive-only contract rule):**
- **Env knobs.** Every numeric limit below reads an optional env override, and `0` disables that control: `TRPC_MAX_BATCH_SIZE` (25), `MUTATION_LIMIT_PER_MINUTE` (60), `MUTATION_LIMIT_PER_HOUR` (1000), `DECRYPT_LIMIT_PER_MINUTE` (30000), `JOURNAL_ENTRY_QUOTA` (5000), `JOURNEY_QUOTA` (200). A miscalibrated limit can then be relaxed in DigitalOcean without a code change. The content-type gate has its own switch: `TRPC_JSON_ONLY_POSTS=0` turns it off, and it is on by default. The other controls (headers, errorFormatter, ownership checks, lock key) have no knob; they are backed out by reverting their commit.
- **`/api/trpc` request guard** (Express middleware mounted on `/api/trpc` before `express.json()` and the tRPC adapter, so it runs before body parsing; `clerkMiddleware` is app-wide and still runs first):
  - Batch cap: more than **25** procedures in the path → HTTP 400. Procedures are counted the way tRPC parses them: comma-split after `decodeURIComponent` (tRPC's `resolveResponse`), so `%2C` counts as a comma. The response is one tRPC-shaped error object (`BAD_REQUEST`, superjson `{json: …}` envelope). It applies to GET (queries) and POST (mutations) alike, because both carry the procedure list in the path. A single non-array error body is valid for a batch: `httpBatchLink` applies it to every op (`Array.isArray(res.json) ? res.json : batchOps.map(() => res.json)` in @trpc/client). Headroom: the app has ~10 distinct queries, no per-item query fan-out in any released build, and the stream link uses `maxItems: 1`, so real batches stay well under 25. Real batch sizes cannot be measured from the repo, which is why the cap is 2.5× the query count rather than tight. A 400 is not retried.
  - Content-type gate: a POST must be `application/json` (any parameters) → otherwise HTTP 415 (`UNSUPPORTED_MEDIA_TYPE`). `@trpc/client` (`httpUtils`) sets `content-type: application/json` on every non-GET request, including input-less ones such as `user.remove`. No released build sends any other POST to `/api/trpc` (see the released-client evidence). A POST with no content-type is already rejected today by tRPC with `UNSUPPORTED_MEDIA_TYPE`, so that case does not change. A server test drives the real `httpBatchLink` and `httpBatchStreamLink` against the guard to confirm this. Why this closes cross-site CSRF: an HTML form can only send `multipart/form-data`, `text/plain` or urlencoded, all now rejected; a cross-site `fetch` with `application/json` needs a CORS preflight, and the server's `cors()` answers with `Access-Control-Allow-Origin: *` and no `Allow-Credentials`, so the browser never sends the credentialed request.
- **Security headers** (hand-rolled middleware, no new dependency): `Content-Security-Policy: frame-ancestors 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security: max-age=31536000` only when `req.secure` (true behind the proxy via `trust proxy` 1 and `X-Forwarded-Proto: https`); `app.disable("x-powered-by")`. A full script/style CSP is deferred (Expo web + Clerk + Turnstile + Sentry need live verification). The frame headers also cover the static Expo web build. Nothing embeds the app in a frame: Clerk sign-in runs inside the app's own page, and Turnstile frames Cloudflare's origin, not ours.
- **Clerk `authorizedParties`**: opt-in via new optional env `CLERK_AUTHORIZED_PARTIES` (comma-separated origins). Unset = today's behaviour. Not on by default because a wrong value returns 401, which logs every client out (knowledge: 401 auto-logout), and whether native clerk-expo tokens carry an `azp` claim is unverified. The knowledge entry documents how to verify and enable it.
- **Shared rate-limit helper**: a new `createRateLimiter({ limits, message })` (rolling windows per user id, rejected attempts not recorded, idle users swept above a size threshold like `chatRateLimit`). `chatRateLimit` itself is left as it is.
- **Per-user mutation rate limit**: a tRPC middleware on the shared `procedure` counts every mutation by an authenticated user: 60 per rolling minute, 1000 per rolling hour → `TOO_MANY_REQUESTS` (already a user-facing code). Chat mutations count toward it too; they are already capped at 20/minute by `chatRateLimit`, so they can use at most a third of it, and the stricter chat limiter still decides chat. Headroom: no released build has looped or fan-out mutations (journey reorder is one mutation carrying all items), so each mutation is one user action. 60 a minute means one action every second for a full minute, beyond rapid tapping. Mutations never retry, so a rejection never multiplies.
- **Per-user decrypt budget** (a high backstop, not a normal-load limiter): the encryption service counts decrypted values per user, 30,000 per rolling minute → `TOO_MANY_REQUESTS`. A new `decryptMany(ctx, identifier, values)` **reserves the whole count before decrypting anything**, so a rejected request does no work; `journal.list` and `decryptMessages` use it, and single `decrypt` reserves 1. Calibration: a journal entry has one encrypted field (`content`), so a full `journal.list` at the 5,000-entry quota costs 5,000 decrypts. That is 6 full lists a minute at quota, or 60 for a 500-entry user. Several devices or tabs share the budget. Even three clients listing a 5,000-entry journal at once stay at half of it. The released app retries a 429 query up to 3 times; each retry is again rejected before doing any work, so retries add requests but no decrypt cost. Every decrypt call site is a user-scoped route (journal get/list, conversation get, sponsor chat and retry). The budget keys on the session user id (`requireUserId`), so there is no shared "system" bucket.
- **Quotas** at create time, soft (a count then an insert, so parallel requests can overshoot slightly; acceptable for an abuse cap): 5,000 journal entries per user (counting check-in journal entries) and 200 journeys per user → `FORBIDDEN` with a plain message (a user-facing code; 403 is not retried and does not log out). Only new rows beyond the quota are refused; existing data is never touched. Headroom: 5,000 is more than 13 years of daily journaling.
- **User upsert**: `database/user/upsert` reads first and writes only when the user is missing or a valid header timezone differs from the stored one.
- **Fail-closed dev flags**: `initTRPC.create` gets an explicit `isDev: NODE_ENV === "development"`; Clerk `debug` uses the same check through a small exported helper so it is testable. A tRPC `errorFormatter` replaces the message of an INTERNAL_SERVER_ERROR whose `cause` is a non-tRPC error (tRPC's wrapping of a thrown plain `Error`) with a generic one; deliberate `InternalServerError(...)` messages and every non-500 code (including UNAUTHORIZED) are untouched. The work step audits route and datasource `throw new Error(...)` sites: none maps to a user-facing code today, and the released app already shows its own fallback for 5xx.
- **Ownership in the query**: `checkin.getOrCreate` verifies `journey.userId` before its upsert; `schedule.getByCheckInId` and `schedule.remove` take `userId` and filter on it; callers updated.
- **Conversation lock** keyed by `${userId}:${conversationId}`.
- **Dead code**: remove the token-string branch of `createContext`. No caller passes a string: the tRPC adapter passes the Express request, cron passes nothing and migrations pass `undefined`. No client can reach it.
- **Expo push**: optional `EXPO_ACCESS_TOKEN` env passed to `new Expo({ accessToken })`. It only affects server-to-Expo calls; unset keeps today's behaviour.
- **Dependencies**: targeted `npm update` of `@clerk/express` (pulls `@clerk/backend`), `body-parser`, `path-to-regexp`; not a blanket `npm audit fix`. This is the only change that could move the app's native fingerprint. If the production fingerprint (computed by `packages/app/scripts/eas-deploy.sh predict`, the same logic eas.yml uses) differs from main's, the dependency bump is dropped from this PR and recorded in a GitHub issue, and the user is told finding 8 stays open. That way the privacy fix's over-the-air path never depends on it. `predict` is re-run after the final rebase, immediately before ship. After merge, the eas.yml run is checked to confirm it took the update path and published.

**Accepted limitations** (recorded in the knowledge entry): every in-process limiter (mutation, decrypt, the existing chat limiter, the conversation lock) counts per server instance and resets on deploy; the limits assume DigitalOcean runs one instance. A multi-account attacker still gets N× the per-user budget.

API contract (released apps): no procedure renamed or removed, no input tightened, no output shape changed. New rejections only at abusive volumes or for malformed requests, using `TOO_MANY_REQUESTS`, `FORBIDDEN`, `BAD_REQUEST` and `UNSUPPORTED_MEDIA_TYPE`. None is ever `UNAUTHORIZED` or HTTP 401, and no new message contains "Token expired" or "Invalid token" (authorizedParties stays opt-in).

### Candidate approaches considered
- **A (chosen)**: above.
- **B (edge controls)**: same app fixes, batch cap only in code; leave rate limiting and quotas to DigitalOcean/Cloudflare edge rules. Rejected: no edge config lives in this repo (not reviewable or testable here), and edge rules cannot be per-user or cost-aware.
- **C (strict by default)**: A plus `authorizedParties` on by default and a full `helmet` CSP. Rejected for now: both risk locking out users (UNAUTHORIZED → logout for all clients if native tokens carry an unexpected `azp`; a CSP that blocks Clerk/Turnstile/Sentry breaks web sign-in) and need live verification this run cannot do.

## Success criteria
1. Each Goal finding is either closed by a change in this PR or listed under the Goal's residuals with its documentation in a knowledge `reference` entry.
2. `loggerLink` in `TRPCProvider.tsx` is enabled only when `__DEV__`.
3. Sentry.init passes a `beforeBreadcrumb` that drops console breadcrumbs and strips query strings from http breadcrumb URLs, and `tracesSampleRate` is 0.1 outside `__DEV__`; the pure scrub function's behaviour is checked by a `node --experimental-strip-types` script whose run is recorded in the scratchpad.
4. A notification tap navigates only for relative `/(auth)/…` paths; absolute, protocol-relative, backslash and `scheme:` URLs fall back to the dashboard; checked the same way.
5. Server tests: a `/api/trpc` batch of 26 procedures gets HTTP 400 with a tRPC-shaped error object, for both GET and POST, including when the commas are `%2C`-encoded; 25 passes through; `TRPC_MAX_BATCH_SIZE=0` disables the cap.
6. Server tests: a POST to `/api/trpc` with `multipart/form-data`, `text/plain` or `application/octet-stream` gets 415; `application/json` (with or without a charset) passes; GET is unaffected; `TRPC_JSON_ONLY_POSTS=0` disables the gate. A test drives the real `@trpc/client` `httpBatchLink` and `httpBatchStreamLink` (an input-less mutation included) through the guard and gets through.
7. Server tests: responses carry `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff` and the referrer policy; HSTS appears with `X-Forwarded-Proto: https` and not without it; no `X-Powered-By`.
8. `CLERK_AUTHORIZED_PARTIES`, when set, is parsed and passed as `authorizedParties` to `clerkMiddleware`; when unset, the option is absent (unit test on the option builder).
9. Server tests: the 61st mutation in a minute (and the 1001st in an hour) from one user gets `TOO_MANY_REQUESTS`; queries are not counted; another user is unaffected; idle users are swept. Tests also cover the env knobs: each one overrides its default, and `0` disables its control (mutation, decrypt and both quotas).
10. Server tests: a `decryptMany` that would take one user past 30,000 values in a minute throws `TOO_MANY_REQUESTS` before decrypting anything; another user is unaffected.
11. Server tests: `journal.create` / `checkin.create` with a journal entry at 5,000 existing entries, and `journey.create` at 200 journeys, return `FORBIDDEN`; below the quota they succeed.
12. Server tests: `user.upsert` does not write when the user exists and the timezone is unchanged or invalid, and writes when it is new or the valid timezone differs.
13. `initTRPC.create` sets `isDev` explicitly and it and Clerk `debug` are true only when `NODE_ENV === "development"`; server tests show an INTERNAL_SERVER_ERROR wrapping a plain `Error` returns a generic message, `new InternalServerError("x")` keeps "x", and an `UnauthorizedError` keeps its code, its message and HTTP 401. An UNAUTHORIZED error whose message contains "Token expired" passes through unchanged.
14. Server tests: `checkin.getOrCreate` returns null and creates no row for a journey the user does not own; `schedule.getByCheckInId` and `schedule.remove` filter on `userId`.
15. The conversation lock key includes the user id at every call site (sponsorChat, streamSponsorChat, retrySponsorChat, remove).
16. `createContext` no longer has a token-string branch.
17. `EXPO_ACCESS_TOKEN`, when set, is passed to the Expo client.
18. Either `npm audit --omit=dev` no longer lists `@clerk/express`, `@clerk/backend`, `body-parser` or `path-to-regexp` and the existing server tests (auth included) pass, or the bump was dropped because it changed the fingerprint and a follow-up records it. In the dropped case, the follow-up is a GitHub issue, and the bump's `package.json` and lockfile changes are removed from the branch. That includes a drop triggered by the pre-ship re-check. In both cases the app's production fingerprint from `eas-deploy.sh predict` equals main's, and this is re-checked after the final rebase.
19. `npm run build` and `npm run test` pass.
20. No tRPC procedure is renamed or removed, no input schema is tightened, and no output shape changes. This is checked by reviewing every `procedure` / `.input(` / `.output(` line in `git diff main`, and the scratchpad records which lines were reviewed. A second, mechanical check covers auth signals. Scope: lines added under `git diff main -- 'packages/server/src/**/*.mts'`, excluding `*.test.mts` files and comment lines. None of those lines may contain `UNAUTHORIZED`, `UnauthorizedError`, `401`, "Token expired" or "Invalid token". The one exception is the errorFormatter's pass-through condition, and the scratchpad records the grep output.
21. The PR has separate commits for each control, with the app commits apart from the server commits.
