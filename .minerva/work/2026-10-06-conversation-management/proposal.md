# Proposal: conversation-management

**Date**: 2026-10-06
**Status**: Shipped (2026-10-06)
**Closes**: #31

## Goal

Let Sponsor-chat users manage their conversations: delete one (with confirmation), rename one, page through a long drawer list and a long message history (older messages load on scroll up) with a virtualized message list, and retry a message whose reply failed without saving it twice. Released App Store builds keep working unchanged against the new server (epic #34 API compatibility rules).

## Why

GitHub issue #31 (epic #34, Wave 2). Conversations are sensitive and cannot be deleted from the app; titles cannot be changed; the drawer loads every conversation and the chat loads and renders every message in a plain `ScrollView`. Wave 1 (#25) added the server pieces (`conversation.remove`, optional `cursor`/`limit` on `list`/`get`, `updateTitle`, `setTitleIfNull`) but no client uses them and no rename route exists. Wave 1 (#28) left a known defect for this unit (knowledge `2026-10-06-decision-sponsor-chat-client-cache-model`): after a failed generation the server has already saved the user message (persist-before-generate, owner-approved) and the client also restores the typed text, so re-sending duplicates it on the server.

## Approach

File ownership (issue #31 + coordinator): `packages/app/src/providers/ConversationProvider/**`, `components/ConversationDrawerContent/**`, `components/pages/SponsorPage/**`, `app/(auth)/(drawer)/**`, server `network/rpc/route/conversation/**` and `database/conversation/**` (additive only). No Prisma migration, no new npm dependency. Crisis prompt files untouched.

### Server (additive only; no existing procedure's input/output/behavior changes)

1. **`conversation.rename`** (new mutation). Input `{ conversationId: z.uuid(), title: string }`; the title is normalized by transform (newlines/tabs → space, whitespace collapsed, trimmed, capped at 100 chars at a word boundary) and rejected only if empty after normalization (new procedure, so a zod BAD_REQUEST is acceptable; never UNAUTHORIZED). Output `{ conversation: { id, title, createdAt, updatedAt } }` (same shape as `remove`/`create`). Not found / not owned → `NotFoundError("Conversation not found.")`. New database function `database/conversation/rename.mts` writes the title with a single raw `UPDATE "Conversation" SET "title" = $1 WHERE "id" = $2 AND "userId" = $3` so `updatedAt` (Prisma `@updatedAt`) is NOT bumped: renaming is not activity and must not reorder the drawer or move a row across a list-page cursor; then re-reads the row. (Table/columns verified in the initial migration: `"Conversation"`, `"id"`, `"userId"`, `"title"`, no `@@map`; the tagged-template `$executeRaw` is parameterized. Rejected alternative: Prisma `update` with an explicit `updatedAt: existing.updatedAt` needs read-then-write and can overwrite a concurrent message's `updatedAt` touch with a stale value.) This is the first raw query in `packages/server/src`, so the database test mocks `$executeRaw`. **Auto titles can never overwrite a rename**: the only auto-title writer is `setTitleIfNull` (conditional `updateMany ... WHERE title IS NULL OR title = ''`), and a rename always stores a non-empty title, so a title generation racing a rename either lands first (and is then replaced by the rename) or finds a title and writes nothing. A server test pins this (setTitleIfNull after rename → no write; rename after auto title → rename wins). Existing `updateTitle` stays untouched.

2. **`conversation.retrySponsorChat`** (new mutation), the "retry this message" action. Input `{ conversationId: z.uuid(), messageId: z.string() }`. Under the same per-conversation lock as `sponsorChat`: load the newest page (ownership check), require that the newest message IS `messageId` and is a `USER` row (i.e. still unanswered); otherwise throw `TRPCError CONFLICT` "This message can no longer be retried." (missing conversation → NotFound). Then decrypt that message's text and run the same generation tail as `sponsorChat` (history from the DB excluding the retried row, re-appended last; journeys/check-ins context; blocked → fallback reply; truncated → error; persist the MODEL reply; title generation when untitled) WITHOUT persisting a user message. Output `{ response, userMessageId, modelMessageId }` (same as `sponsorChat`). Implementation: extract the post-persist half of `runTurn` into a shared `generateReply(...)` used by both; `sponsorChat`'s input, output, persistence order and errors are unchanged (existing `runSponsorChat` tests stay green; new tests cover retry: happy path saves exactly one MODEL row and no USER row; non-latest / answered / MODEL id → CONFLICT; generation failure → error, nothing saved).

### Client

3. **Message history pagination + virtualization.** `conversation.get` moves from `useQuery` to tRPC `useInfiniteQuery` (`infiniteQueryOptions({ conversationId, limit: 30 })`, `getNextPageParam: page => page.conversation.nextCursor ?? undefined`), keeping the #28 freshness model (`staleTime: Infinity`, explicit refetch only, same retry policy, no `get` invalidation on the send path). `pages[0]` is the newest page; the flattened chronological list is `pages` reversed and concatenated. A send appends the user message + reply to the END of `pages[0]` under the same client id as the pending bubble (the #28 id-keyed merge is unchanged). SponsorPage renders an **inverted `FlatList`** (data newest-first, `keyExtractor` by id, `onEndReached` → load older, spinner at the top while loading older, `ThinkingIndicator` as the inverted list header so it sits at the bottom); the manual `scrollToEnd` effect goes away because an inverted list is anchored at the newest message. The reversed array is memoized and `onEndReached` is guarded by `hasNextPage && !isFetchingNextPage` (it can fire immediately when content is shorter than the viewport). The flattened message list is de-duplicated by id (page boundaries can shift after local appends to `pages[0]`), and all helpers handle an absent / empty `pages`. react-native-web 0.21.2's VirtualizedList carries an inverted-wheel handler (verified in `node_modules/react-native-web/dist/vendor/react-native/VirtualizedList`); web behavior (wheel direction, text selection, keyboard) is a named manual check; if it fails on web, the fallback is a non-inverted `FlatList` on web only (scroll-to-end on new messages, older pages prepended) behind `Platform.OS`. Older-page loads are refused while a send/retry/refresh is pending for the conversation or its query is fetching (a TanStack `fetchNextPage` writes back the pages it started from, dropping a concurrent append), the message `FlatList` is keyed by conversation id so a switched-to conversation opens at its newest message, and rename cancels an in-flight older-page fetch before writing the title. Explicit refetches of a conversation (select of a cached conversation, error-view Retry, failed send/retry) first cancel in-flight fetches, then trim the infinite cache to its newest page and refetch with `cancelRefetch: true` (`pages` and `pageParams` trimmed together; covered by the verify script), so a refetch is one request regardless of how far the user scrolled. The cached newest page still renders instantly on reopen; only older pages reload on scroll.

4. **Drawer pagination.** `conversation.list` moves to `useInfiniteQuery` (`{ limit: 20 }`, opaque cursor). `conversations` is the flattened pages de-duplicated by id (a row whose `updatedAt` moved between page fetches can appear twice). Drawer `FlatList` `onEndReached` → next page with a footer spinner. Existing list invalidations (after send, title refresh timers, create) keep working (an infinite query refetches all loaded pages).

5. **Delete.** Each drawer row gets a visible "more" button (works on web, where long-press is not discoverable) and, on native only, `onLongPress` (tamagui's web press handler fires `onLongPress` on every click), both opening a small actions modal (Rename / Delete / Cancel) built on the existing `AlertModal` pattern (react-native `Modal`; `Alert.alert` is a no-op on web). Delete asks for confirmation ("Delete this conversation? This can't be undone."), then calls `conversation.remove`. On success, or on NOT_FOUND confirmed by a one-off full `conversation.list` (own cache key) that no longer contains it (the server also maps database errors, and an older server an unknown procedure, to NOT_FOUND; otherwise a "Failed to delete" toast): drop it from the list cache, `removeQueries` its `get` cache, clear its failed draft, and if it was the active conversation switch to the most recent remaining loaded conversation, or, if none remain, re-run init (`getOrCreate` → a fresh empty conversation = the empty state). Delete is disabled for a conversation with a send in flight. A released build on another device that has the deleted conversation open keeps its current behavior: its next `get`/`sponsorChat` returns the existing NotFound (no new error codes; server unchanged here).

6. **Rename.** Actions → Rename opens a modal with a text input prefilled with the current title (empty for the "New conversation" placeholder), Save/Cancel, `maxLength` 100; Save is disabled while the trimmed input is empty (a rename cannot clear a title back to the placeholder). On success update the title in the list cache and in every page of that conversation's `get` cache (header title updates immediately), then invalidate the list.

7. **Retry a failed message; stop restoring saved text.** Before a send the provider snapshots the set of server (non-`pending-…`) message ids in the conversation's cache. On a failed send the provider (still showing the pending bubble) trims the conversation's infinite cache to its newest page and refetches it (one request, not every loaded page; older pages reload on scroll), then classifies with a pure helper (`classifyFailedSend`): walking back past trailing MODEL rows, the newest `USER` row counts only if its id is a server id NOT in the pre-send snapshot and its content equals the exact trimmed string the client sent (the server's `chatInput` only trims, and `runTurn` persists that string). Outcomes: `saved-unanswered` (input clears, `sendMessage` resolves `true`, toast "Your message was saved, but no reply came back.", Retry shown), `answered` (message and reply both stored, only the response was lost: input clears, error reported but not toasted), `not-saved` (persist failed, network error, an older identical message, or the refetch itself failed: error toast and the draft is restored exactly as today); in the refetch-failed case a later Retry/re-send can still duplicate, which is the accepted pre-existing behavior. A schema-backed idempotency key (client message id) would make this exact but needs a migration, which this unit excludes. The chat shows a "No reply yet · Retry" affordance under the trailing message when it is a `USER` message with a server (non-`pending-…`) id and no send/retry is in flight for the conversation (this also covers unanswered messages left by released builds). Retry calls `conversation.retrySponsorChat` with that id, reuses the per-conversation pending/`isThinking` state (no new bubble), appends the reply with the server's `modelMessageId` on success, and on failure toasts and refetches. A CONFLICT (already answered elsewhere) refetches and shows the server state. The affordance wording is "No reply yet · Retry" because it also covers a truncated reply (user message delivered, no reply stored). Residual risk, same as `sponsorChat` accepts: the per-conversation lock is best-effort (20s bounded wait, single process), so two concurrent retries from two devices could in theory both generate a reply; the client disables Retry while one is in flight.

8. **Pure modules + verification.** Cache/list/retry logic lives in a pure module (`providers/ConversationProvider/conversationCache.ts`: flatten pages, append to newest page, dedupe list, remove/rename in list pages, set title in get pages, next conversation after delete, retryable message id, "send confirmed saved") verified by a committed `npx tsx .minerva/work/2026-10-06-conversation-management/verify-conversation-management.ts`. Server: node tests for `rename`, `retrySponsorChat`, the rename/auto-title interplay.

### Compatibility statement

API contract: additive only. New procedures `conversation.rename`, `conversation.retrySponsorChat`. No existing procedure's input or output changes. Server scope note: issue #31 says "rename route only", but the coordinator assigned this unit `route/conversation/**` + `database/conversation/**` (additive) and the retry follow-up from #28; the `runTurn` → `generateReply` extraction is behavior-preserving and pinned by the unchanged `runSponsorChat` tests. tRPC's `infiniteQueryOptions` always sends an extra `direction` key; `list`/`get` inputs are non-strict `z.object`s that strip it, so they must never be made `.strict()`. A new native client against the previous (production) server degrades gracefully: `list`/`get` ignore the unknown `cursor`/`limit`/`direction` keys and return full results with no `nextCursor` (paging simply ends); `remove`/`rename`/`retrySponsorChat` fail with a toast (deploy order is server first).

## Success criteria

1. `conversation.rename` exists, is additive, normalizes the title, does not bump `updatedAt`, returns NotFound for missing/unowned conversations; server tests prove an auto title (`setTitleIfNull`) never overwrites a renamed title.
2. `conversation.retrySponsorChat` exists, regenerates a reply for the newest unanswered USER message without saving another USER row, rejects (CONFLICT) any other message id, and reuses `sponsorChat`'s generation path; `sponsorChat` behavior and its existing tests are unchanged; new server tests cover these cases.
3. The drawer can delete a conversation (confirm first); deleting the active one switches to the most recent remaining conversation or to a fresh empty one; NOT_FOUND on delete is treated as already-deleted.
4. The drawer can rename a conversation; the new title shows in the drawer and header without reopening the conversation.
5. The drawer list and message history paginate via the optional `cursor`/`limit` (older messages load on scroll up), and the message list is a virtualized (inverted) `FlatList`.
6. After a failed send whose user message the server saved, the text is not restored to the input and the message shows a Retry action that produces a reply without duplicating the message; when the server did not save it (including when an older identical unanswered message exists), the text is restored as before. The verify script covers the "confirmed saved" helper including the identical-older-message case, and the pending bubble staying visible through the trim-and-refetch (id-keyed merge).
7. `npm run build`, `npm run test`, server lint stay green; the verify script passes; the PR body lists iOS/Android/web manual steps (including web inverted-list scrolling/selection) and the API-contract line.
